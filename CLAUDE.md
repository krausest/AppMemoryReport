## Overview

a macOS-only Swift command-line tool plus a SwiftUI GUI that reports the total memory used by each proecess, including all their helper/XPC/renderer/sub processes. Both the CLI and the GUI are localized (English source strings, German translation) and follow the system language.

The goal is to sum the memory a process like a browser actually occupies. This includes subprocesses but respectes shared memory.

## Commands

```sh
swift build                     # debug build
swift build -c release          # release build
swift run app-memory-report     # build and run the CLI
swift build && sudo .build/debug/app-memory-report   # CLI for all users
swift run AppMemoryReport       # build and run the GUI (no .app bundle; the lock button needs the CLI built too)
swift test                      # MemoryCoreTests (Swift Testing)
scripts/make-app.sh             # release build of the GUI as AppMemoryReport.app (ad-hoc signed)
```

The app icon (a RAM module) is drawn with CoreGraphics in `scripts/make-icon.swift`; `make-app.sh` renders it into an iconset and converts it with `iconutil` to `AppIcon.icns` on every build.
## Architecture

Three SwiftPM targets: `MemoryCore` (library with everything below), `app-memory-report` (CLI, `main.swift` only prints) and `AppMemoryReport` (SwiftUI GUI), plus the test target `MemoryCoreTests`. `groupProcesses` takes the UID, the bundle lookup and the argv lookup as parameters so tests can run on synthetic process tables.

The pipeline is `MemoryReport.measure` in `MemoryCore/MemoryReport.swift`: snapshot processes → group them by root process / app → read each process's `ri_phys_footprint` (ranking, cache check, preliminary rows) → measure each group, plus all PIDs together for the total if requested → unsorted `AppUsage` rows. The CLI requests the total and prints a table. Without root only the current user's processes are shown (footprint can't read others); run the built binary with `sudo` to include all users (never `sudo swift run`, which leaves root-owned files in `.build`); the CLI then adds a User column (owner of the row's root process, `userName(of:)`).

- **`ProcessTable.swift`**: snapshots every visible PID via libproc (`proc_listallpids`, `proc_pidinfo`, `proc_pidpath`). Without root, other users' processes such as the setuid `login` between a terminal and its shell fail `PROC_PIDTBSDINFO` with EPERM, so it falls back to `PROC_PIDT_SHORTBSDINFO` (ppid, uid, flags incl. `PROC_FLAG_CTTY`). `arguments(of:)` reads argv via `KERN_PROCARGS2` (node/npm rewrite it in place, e.g. `["npm run dev", "", ""]`). It also calls the private libSystem function `responsibility_get_pid_responsible_for_pid` (bound via `@_silgen_name`) to get the "responsible" PID, the same attribution Activity Monitor uses (e.g. Safari is responsible for its WebKit XPC services).
- **`Grouping.swift`**: returns `ProcessGroup`s (name, PIDs, UID of the root process, outermost `.app` path for icons). Each process is attributed to a *root* (`Attribution.root`): it steps to the parent (if `ppid > 1`) while the process is responsible for itself or its responsible PID is an ancestor, so every ancestor is visited; otherwise it jumps to the responsible PID (XPC services under launchd); a process with neither is a root. A command started in a terminal is a root of its own: its parent is a *terminal shell*, i.e. a whitelisted shell (`zsh`, `bash`, `sh`, …) with a controlling TTY and no such shell among its ancestors. "Topmost" keeps npm's `sh -c` children with npm, and the TTY check keeps shells that apps spawn without a terminal (e.g. Claude Code's tool shell in VS Code) with the app. Terminal commands are named after their argv (`commandName`, e.g. `npm run dev`, `sh build.sh`). This check comes before responsibility, because shells and commands in Terminal (and current iTerm2) are responsible to the terminal app directly. Attribution runs on the unfiltered table, so a chain can pass through other users' processes (`login` runs as root). Roots whose executable sits in an `.app` bundle are merged per **outermost** bundle ID and root UID, so each user's instance of an app is its own row (nested helper apps count toward their parent; `outermostAppPath` walks the path components and skips directories named `*.app` that aren't bundles) and named after the bundle's display name, localized for the user's languages via `Bundle.localizedString(forKey:…localizations:)` (macOS 15.4+, soft hyphens removed). Other roots are one row each, named after the executable, with `[pid]` / `(bundleID)` appended when names of the same user collide. Rows of different users may share a name, so `AppUsage.id` is `uid/name` and the GUI matches rows by `id`. `satelliteRules` add self-responsible non-bundle roots to a running app: Safari gets its agents (`SafariLaunchAgent`, `SafariBookmarksSyncAgent`, `SafariNotificationAgent`, `com.apple.Safari.History` in a `/usr/libexec/` dir under the Safari cryptex, and the `SafariSafeBrowsing.framework` service), and iTerm2 gets its `iTermServer-*` session servers, including one orphaned by an update (ppid 1). Safari-framework XPC services like `CredentialProviderExtensionHelper` are responsible to their client apps and must not match. The UID filter is applied only after attribution. The tool itself is not excluded, so the GUI shows its own memory (its localized display name, "App Memory Report" / "Speicherverbrauch", when run as an .app).
- **`Footprint.swift`**: `Footprint.measure` runs `/usr/bin/footprint` for one group, writing JSON to a temp file. footprint's `total footprint` counts memory shared between the processes in a group only once, but it only sums the regions it sees as dirty. The kernel's `phys_footprint` can charge more (OrbStack's helper: ~3 GB of its mapped VM disk image counts as clean "mapped file" for footprint), so each process's excess of `auxiliary.phys_footprint` over its `footprint` from the JSON is added to the total. The result is clamped to the sum of `phys_footprint`, so a measurement never exceeds the value a group was ranked by. Groups with a single live process skip footprint and use `ri_phys_footprint` directly; groups where the sum minus the largest process is ≤ max(1 MiB, 1 %) skip it too and use the plain sum, marked `*`. Only live PIDs (those with a `ri_phys_footprint`) are passed to footprint. `MemoryReport` runs all measurements via `parallelMap` (`Parallel.swift`, by default at most one per CPU core). Index 0 is the all-PIDs run behind the total ("Total"/"Gesamt"), so rows can add up to more than the total. A row (or the total) is marked `*` when it is a plain sum of per-process values instead of a deduplicated total. Besides the skip rule above, this happens in two cases:
  - footprint failed to run, so the per-process `ri_phys_footprint` from `proc_pid_rusage` is summed instead.
  - footprint's report contains PIDs that weren't requested. A requested PID that exited in the meantime gets treated as a process *name* pattern and can pull in unrelated processes. Only the requested PIDs' values are summed.
- **Top N** (`measureTop` in `MemoryReport.swift`): with `limit`, groups are ranked by the plain sum of `ri_phys_footprint` and measured in rounds (first `limit + 10`, then 10 more) until the `limit`-th largest result is ≥ the plain sum of the next unmeasured group. Because of the clamp this is exact, not a heuristic.
- **`FootprintCache.swift`**: per group (key: sorted live PIDs) the *shared* amount `plain sum − deduplicated total` from the last footprint run. Reused while the PIDs are identical, the plain sum moved ≤ 2 % and the entry is < 5 min old; the row is then `live plain sum − shared`. Each report returns the cache for the next run (entries not used are dropped). Dedup corrections are small (< 1 % for most apps, 4.5 % for Brave, see `docs/MeasurementExample.md`) and the shared amount barely changes while the PIDs stay the same, so this is safe and saves most of footprint's CPU.
- **GUI** (`AppMemoryReport/`): `MemoryModel` (`@Observable`, main actor) measures without the total (by far the slowest run), passes its `FootprintCache` and, with "Top 30 only" (default), `limit: 30` to `MemoryReport.measure`. Via `progress` it first gets the plain sums of the rows to show (`preliminary`, shown as "≈ …" in secondary color), then each row once measured (`apply`: preliminary values only fill rows not shown yet; updates of a finished run are ignored). It uses at most 4 parallel `footprint`s at `.utility` QoS. `runAutoRefresh` polls once per second and starts a measurement once `interval` (default 30 s; a top-30 refresh costs ~14 CPU-s) has passed since the previous one *finished*, only while a window is visible (the first measurement always runs). `ContentView` shows a sortable `Table` (initially by memory, descending) with search, an interval menu (a `Menu` titled with the current value around an inline `Picker`, because a toolbar `Picker` doesn't reliably show its selection), an "Advanced" checkbox, a lock button and a status bar showing the measurement duration. "Advanced" shows a Shared column: `AppUsage.shared` = `plainSum − bytes`, the memory deduplication removed within the group ("–" for preliminary and `*` rows). `Measurement.plainSum` is the sum of the per-process `phys_footprint` from the same snapshot as `bytes` (for footprint runs: from its JSON, not the earlier `Candidate.phys`), so the difference is never noise from two snapshots; `FootprintCache.store` takes the shared amount from it too. Only the current user's processes until the lock is clicked (`setShowsAllUsers`): `PrivilegedHelper` then starts the CLI binary next to the GUI executable (`Contents/MacOS` in the .app, SwiftPM's bin dir with `swift run`) as root via `osascript` `do shell script … with administrator privileges` (backgrounded, with `-AppleLanguages` so app names follow the user's languages). Measurements then go through the `HelperConnection` and a User column is shown (via `TableColumnCustomization` visibility, because an `if` in a `Table` needs macOS 14.4). Switching modes clears the rows and drops progress of a running measurement; if the helper dies, the model falls back to the user's own processes and shows an alert.
- **Root helper** (`MemoryCore/Helper.swift`): `app-memory-report --serve <socket>` runs `serveHelper`. `HelperConnection.accept` creates a socket in a `mkdtemp` dir (mode 0700) in the GUI's temp folder, runs the launch closure, waits ≤ 10 s for the connection and checks via `getpeereid` that the peer is root (`peerUID` is a parameter for the round-trip test in `HelperTests`). Protocol: JSON lines, request `HelperRequest(limit:)`, answers `.progress([AppUsage])`… then `.report(rows:groupCount:)` (`AppUsage` is `Codable`). The helper measures all users without the total, keeps its own `FootprintCache`, and exits at EOF, i.e. when the GUI releases the connection. `make-app.sh` copies the CLI into `Contents/MacOS` and signs it before the bundle.
- **Localization**: each executable target has its own `Localizable.xcstrings` (source language `en`, `defaultLocalization` in `Package.swift`). SwiftPM doesn't extract strings, so new keys must be added to the catalog by hand. Keys use the `%lld`/`%@` form of the interpolation, and code calls a `localized("…")` helper instead of SwiftUI's implicit lookup. Foundation picks a resource bundle's language from the *main* bundle's localizations, which the CLI and `swift run` don't have, so they would always get English. `preferredLocalization(of:)` (`MemoryCore/Localization.swift`) therefore picks the `.lproj` folder via `Locale.preferredLanguages` itself. The CLI looks up its resource bundle next to the executable without `Bundle.module`, which would crash if the bundle were missing; English keys are shown then. In the GUI, with `swift run` the strings come from `Bundle.module`. `make-app.sh` instead copies the compiled `.lproj` folders, plus `InfoPlist.strings` with the localized app name, into the app's own `Contents/Resources`, and `localized` then uses `Bundle.main`. That way AppKit's standard menus are localized too. `formatBytes` always shows MB with one decimal (no GB), using the user's decimal separator.
